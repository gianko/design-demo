# Eval runs are a budgeted standalone script, compared after the fact

An eval run is `pnpm eval`, a standalone `tsx` script that imports the generator's `generate()` and calls it in-process, not a Vitest suite. In an eval a failing rep is data, a pass rate spans K reps, the dollar budget is state shared across every rep, and the output is one results JSON. Vitest would read each failure as a red build, isolate reps in workers that can't share a budget, need a custom reporter and raised timeouts, and re-run (and re-spend) in watch mode. Vitest still tests the runner's pure parts: pass criteria, aggregation, pricing and comparison. Two prompt or registry versions are compared after the fact from two committed results files, because the registry is whatever code is checked out and can't vary inside one invocation.

## Decisions that come with it

- **A rep** is one `generate()` run of one screen brief through the repair loop. Each attempt records gates 1, 2, 3 and 4 and the P0 taste rules (gate 7), all hard; the screen brief's pass criteria are checked once on the final UI spec. Gate 6 never runs in an eval: a fresh generated screen has no baseline. Gate 5 joins as a soft column once it exists. What each attempt logs, and which failures go back into repair turns, is [ADR 0010](0010-each-generator-step-repairs-itself-from-normalised-gate-failures.md).
- **What renders.** Gate 4 and the render-time taste rules see light and dark × every declared screen state plus the default, at the density the screen brief's audience sets ([ADR 0001](0001-density-by-audience.md)). A failure names its theme and screen state.
- **Outcomes.** A rep ends as pass (every hard gate and pass criterion holds within the attempt limit), fail (attempts ran out), error (infrastructure broke: API overload after SDK retries, a timeout, a harness crash) or skipped (the budget ran out first). Errors and skips are counted but left out of pass rates. Each screen brief reports a first-attempt pass rate and a final pass rate; the gap between them is what the repair loop is worth.
- **Pass criteria** live in the screen brief's frontmatter as `requires.components`, `requires.states` and `requires.actions`, checked deterministically against the final UI spec. a11y is gate 4. Motion joins as `requires.transitions`, structural patterns on the same UI spec ([ADR 0011](0011-motion-follows-declared-state-changes-owned-by-the-library.md)).
- **Cost is capped in dollars.** `--budget <usd>` (default 15, `none` for no cap) is checked against cost computed from logged `usage` ([ADR 0003](0003-generator-on-messages-api-not-an-agent-loop.md)). At the budget the runner stops starting reps and lets in-flight ones finish. Before starting, it prints an estimate (screen briefs × K × the median rep cost of the latest results file) and asks to confirm when it exceeds the budget. The Console spend limit stays the backstop.
- **Defaults.** K = 3, concurrency 3, each rep in its own working directory. `--briefs <glob>` (default `evals/briefs/*.md`) and `--k` are the only ways to narrow a run. Both are recorded, and a comparison flags runs whose brief sets differ.
- **No resume.** A capped or interrupted run ends as it stands. Re-running skipped reps with `--briefs` gives a separate results file, so one file never mixes two moments.
- **Version tuple.** Every results file records the spec and code prompts' content hashes, the registry hash ([ADR 0004](0004-flat-library-only-ui-spec-and-zod-first-registry.md)), model and effort per step, the git SHA and a `--label`. The runner refuses a dirty tree unless given `--allow-dirty`, and records it if so.
- **Committed vs scratch.** `evals/results/<YYYY-MM-DD>-<label>.json` is committed: the version tuple, run totals, and per rep its outcome and per attempt its gate results with failure messages, usage, cost and wall time. `evals/runs/<run-id>/` is gitignored scratch holding every attempt's UI spec, TSX, raw gate output and screenshots. A failure worth showing is copied out by hand.
- **The report is HTML.** `pnpm eval:report <a.json> [b.json]` writes one self-contained HTML file (inline CSS, no CDN) to gitignored `evals/reports/`, styled with the design system's own `tokens.css`. One file gives a run report; two give the side-by-side comparison: counts per screen brief and overall (`2/3 → 3/3`), not percentages, with no claim of significance at K≈3; mean attempts, cost, wall time and per-gate failure counts. Screenshots of each rep's final and failing attempts are embedded when the run's scratch folder exists locally, and left out otherwise. The README table (P2) is markdown from the same aggregation. The newest committed results file's report is deployed to GitHub Pages at `/evals/`, without screenshots ([ADR 0009](0009-gates-render-in-one-pinned-linux-arm64-image.md)).

## Considered options

- **Vitest as the runner, each screen brief a test with K reps**: see above.
- **Capping the number of reps** (demo brief §9 Q10's wording): simpler, but a rep's cost varies 3–4× with its attempts.
- **A/B of two configs in one invocation**: can vary prompts and model but not the registry without two worktrees.
- **Message Batches API**: 50% cheaper, but each repair attempt waits on the last one's gates, so a rep becomes several batch round trips, and structured outputs in batches are undocumented. Worth revisiting if spend becomes the constraint.
- **Resuming a partial run**: see "No resume".
- **Taste lint as a soft column at first**: a better-looking early pass rate that says less, when the library already passes taste lint clean.
- **Markdown as the report**: no room for screenshots, which are what a design audience reads.
