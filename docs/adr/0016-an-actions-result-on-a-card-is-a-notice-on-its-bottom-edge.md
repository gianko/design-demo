# An action's result on a Card is a Notice on its bottom edge

On payment-status, the result of Send reminder was a live Text in the Card's footer: plain ink, the same look as the due date and client lines above it, so it didn't read as a result, and a failure had no look of its own (Text's GAPS.md, "No error or success tone"). It also came and went only with the screen-state crossfade. So an action's result on a Card that is still on screen in the state the action enters is a **Notice**: a full-width strip in a new Card slot, `result`, along the Card's bottom edge, inside its frame under a `line` hairline, with its bottom corners following the Card's radius. A table's result, or one whose Card has left, is a Toast ([ADR 0013](0013-bulk-actions-live-in-datatables-footer-results-are-toasts.md)). No result is a live Text any more. Four takes were prototyped on the payment-status Card in draft [PR #357](https://github.com/gianko/design-demo/pull/357) (variant C won; not for merge, it is the visual source). This amends [ADR 0004](0004-flat-library-only-ui-spec-and-zod-first-registry.md) and [ADR 0011](0011-motion-follows-declared-state-changes-owned-by-the-library.md), and supersedes part of ADR 0013. Decided in [#356](https://github.com/gianko/design-demo/issues/356).

## Decisions that come with it

- **Notice lives in Card's `result` slot,** which allows only Notice. Card draws the slot because the strip escapes the Card's padding and follows its corners, which nothing inside the body or footer can do. A Notice is an icon and the result's copy, the icon a Phosphor icon at regular weight, the density's icon size, in the copy's colour.
- **Two tones.** Success is `surface-raised` with `ink` and `CheckCircle`, matching the success Toast; not the `paid` green, which would read as one more status beside the Card's StatusTag. Failure is a new, quieter inline error pair, `bg-error-inline` with `text-error-inline` (`color.bg.error-inline` and `color.text.error-inline`), AA in both themes, with `WarningCircle` ([#359](https://github.com/gianko/design-demo/issues/359)). `bg-error` stays the Toast's: it was tuned for a floating surface, and edge to edge in a Card it is the loudest thing on the screen. Colour never carries the result alone; the copy says what happened and, on a failure, what to do next.
- **Where a result goes.** A Notice if the action's Card is still shown in the state the action enters; otherwise a Toast. A table's result is always a Toast. So payment-failed's Toasts and withdraw-invoice's failure Toast become Notices, and invoice-queue's table results, until now live Texts, become Toasts.
- **Motion stays inside ADR 0011's "every screen-state change is a View Transition", with no exception.** The Card holding a Notice carries a library-owned view transition name, and its group animates the Card's height. The old and new snapshots stay pinned to the top at their natural size and are clipped by the group, never stretched, so the strip is uncovered as the Card grows and covered as it shrinks. A Button that the new state drops (Send reminder, once sent) collapses away in the same change. Entering runs at `base`, with `ease-settle` under `confirm` and `standard` under `fail`; leaving runs at `base-exit` with `exit`. Under reduced motion it is the existing `fast` crossfade, with no height motion.
- **Retry.** While a retry is pending, the failure Notice stays as it is: the Button's progress edge shows the wait, nothing claims success early, and the "try again" copy stays in view. A retry that succeeds changes the Notice's tone in place (colours and icon swap) rather than collapsing and reopening. A repeated failure doesn't replay: the Notice stays put. A Notice never dismisses itself and has no close button; it leaves only when a state change drops it.
- **Focus moves to the Notice.** When a confirmed result removes the focused Button, focus moves to the Notice, made focusable with `tabIndex={-1}` and showing the focus ring, not to the Screen, so a keyboard user stays on the Card they acted on. This amends ADR 0011's focus rule. ADR 0013 kept focus off a Toast because focus within holds a success Toast's timer; a Notice has no timer, so that reason doesn't apply. The collapse clips only while it animates, so the ring isn't cut off at rest.
- **Announcements don't change.** A Notice's copy is announced politely through Screen's one status region each time its state is entered, a repeated failure's included, as a Toast's is (ADR 0013). A Notice is not an alert: results stay polite, which is also why the name isn't Alert.
- **Text loses `live`.** Its registry `use` line stops sending results to a live Text; a result is a Notice or a Toast.
- **Gate 1 rules.** Notice only in Card's `result` slot. At most one visible result, a Notice or a Toast, per screen state. A Notice only in a state some action's `to` enters. The Card holding the Notice is the one whose footer holds that action's Button, even where the Button is hidden in that state. Tone matches the outcome (success in `to.success`, failure in `to.failure`), for Notice and Toast alike.
- **Pass criteria.** Briefs that show a Card's result list `Notice` under `requires.components` ([ADR 0008](0008-eval-runs-are-a-budgeted-script-compared-after-the-fact.md)). There is no new `requires.transitions` key, and the collapse is not a signature transition: it follows from the structure, which gate 1 already holds.

## Considered options

- **Today's live Text (A):** plain ink in the footer, the same look as the body copy beside it, with no look for a failure; and it would have needed a Text tone, which `.out-of-scope/text-error-tone.md` keeps out.
- **A tinted Notice above the Button (B):** a box inside the Card's padding, a second surface nested in the first, and it pushed the Button down when it opened.
- **A Notice that holds the retry (D):** it takes the Button's place, so the Card's action would sit in its footer in one state and inside the result in another.
- **Animating the live DOM and keeping the Card out of the crossfade** (as the prototype did, by muting the root crossfade while a collapse was mounted): it shows the collapse, but it is an exception to "every screen-state change is a View Transition", and the Card would change outside the transition the rest of the screen runs in.
- **Reusing `bg-error` inline:** the failure Toast's surface, too loud edge to edge in a Card.
- **`InlineResult` as the name:** describes the slot, not the thing; and `Alert` suggests `role="alert"`, which is assertive.
- **A criterion under `requires.transitions`:** the collapse is a consequence of a Notice in a Card's `result` slot, so a presence check on `Notice` plus gate 1's placement rules already covers it.
- **ADR 0013's rejection of "the result inline, in the footer"** doesn't cover a Card. A table's footer competes with a count and several Buttons in a strip sized for controls; a Card's footer holds one Button, and the Notice sits below it, on the Card's edge, not in the footer.

## Consequences

- Eval runs before and after this aren't comparable on payment-status, invoice-review, payment-failed, withdraw-invoice and invoice-queue, whose components or results change; accepted.
- The kept screens whose results move change their renders, so gate 5's calibration set ([ADR 0014](0014-brief-conformance-is-a-soft-vision-judge-proved-by-a-calibration-set.md)) needs re-judging ([#364](https://github.com/gianko/design-demo/issues/364)).
- `.out-of-scope/text-error-tone.md` still holds: a failure's look belongs to Notice, not to a Text tone.
- A fourth Card slot couples Card to Notice, which gate 1's slot allow-list and one-result rule keep in step.
