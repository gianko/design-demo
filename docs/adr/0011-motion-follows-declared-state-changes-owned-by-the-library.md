# Motion follows from declared state changes, and the library owns all of it

The UI spec has no motion vocabulary, and the code step writes no motion. Motion comes from the screen-state changes a UI spec already declares (`states`, `when`, actions and their `to`, slots; [ADR 0004](0004-flat-library-only-ui-spec-and-zod-first-registry.md)), and library components animate those changes with motion tokens, hand-written keyframes and the View Transitions API ([ADR 0002](0002-token-only-tailwind-and-eslint-token-lint.md), [ADR 0005](0005-dtcg-tokens-hand-built-into-css-ts-and-figma.md)). The code step couldn't write motion anyway: generated TSX has no intrinsic elements, library components take no `className`, and `style` is banned. A motion knob in the UI spec would also hand the model a taste call the design brief keeps away from it, since motion only ever confirms what the user did. So a generated screen shows a signature transition by including the components and screen states that carry it. Decided in [Decide how motion attaches to the UI spec and reaches the generated screen](https://github.com/gianko/design-demo/issues/22).

## Decisions that come with it

- **Every screen-state change is a View Transition.** The library exports `useScreenState()`, which returns the current state and `enter(name)`, and every `enter` runs inside `document.startViewTransition`. `useAction(operation, to)` runs one of the fixtures module's mock operations, holds its Button pending, and when the operation settles enters `to.success` with the view transition type `confirm` or `to.failure` with `fail`. `ease-settle` applies only under `confirm`, so settle always follows a confirmed result. DataTable selection enters `rows-selected` through the same `enter`, untyped (`base`, `standard`). Under reduced motion every transition is a `fast` crossfade. Screen exposes its current state as a data attribute.
- **Generated screens hold no state of their own.** A gate 2 rule, `screen-state-via-library`, bans `useState`, `useReducer`, `startViewTransition` and direct calls to the mock operations in generated screens, so nothing can change state outside a View Transition. DataTable owns ticking rows and the open sheet, and the `ScreenHost` holds the selection, as it holds the screen state; Button owns pending.
- **A `ScreenHost` around the screen holds its state, fixture variant and selection.** The library exports `ScreenHost`, which whatever hosts a generated screen renders around it: a story, through the Storybook preview's global decorator, which reads the state and variant from the story's `parameters.screenState`; the gate harness through those stories; later an app. The screen's hooks and the Screen it renders read the same host, so `useScreenState`, `useAction` and Screen's data attribute agree. A generated screen never renders `ScreenHost` itself, which `screen-state-via-library` also bans: it would hold a second state that the stories and the gate couldn't set.
- **Bound data comes from the host too.** `useFixtureData()` returns the data of the host's fixture variant. The code step reads every `{ "bind": "<path>" }` prop ([ADR 0004](0004-flat-library-only-ui-spec-and-zod-first-registry.md)) and every operation argument (`sendReminder`'s invoice id) from it, so a state story's variant reaches the screen's data and its operations alike, and the screen imports nothing but the barrel. `useSelectedRows()` is how a screen reads the selection, the ids of the ticked rows, which it passes to `payInvoices`. A fixture variant may name a starting selection beside its failing operations, outside its data, so no UI spec binds it. A hook rather than props on the screen, because the screen takes no props and its stories name only a state and a variant; rather than an import of the fixtures module, because generated screens import only the barrel and that would let them call the mock operations directly.
- **The pay confirmation is an ActionBar and a Toast.** ActionBar, the bulk-action bar, joins the library in P1: a raised bar shown `when: [rows-selected]` that holds the action's Button. Toast (P1) shows in the action's `to.success` state and is that state's live announcement, in place of a live Text. The library pairs the two by view transition name, so entering the success state morphs the bar into the toast, and the selection clears on a `confirm` transition, inside its update. On failure the bar stays and the rows stay selected, since a `fail` transition keeps the selection, the Button returns to rest, and a failure-tone Toast enters on its own with `standard` easing and no settle. That failure Toast sits inside the bar, in ActionBar's body slot above its Buttons, so the two stay one sticky unit on a long table rather than sticking at the same place (decided in [#243](https://github.com/gianko/design-demo/issues/243)). A failure Toast in a state with no ActionBar stands on its own.
- **Focus follows the view transition name.** When a screen-state change removes the focused element, the library moves focus to the element that takes over its view transition name in the new state, made focusable with `tabIndex={-1}`, or to the Screen if nothing does. A confirmed result that removes the bar's pending Button lands focus on the Toast the bar became, so a keyboard user stays where they acted (decided in [#244](https://github.com/gianko/design-demo/issues/244)).
- **Stagger.** When a transition changes bound statuses in a DataTable, only the rows that changed flip, in row order, one `delay-stagger` (40ms) apart, and from the 8th changed row on they flip together. Unchanged rows don't count, so they leave no gaps.
- **Row → sheet is a `detail` slot.** DataTable gains a `detail` slot, allow-listed to Sheet, holding one template node with row scope as `cell` does. Clicking a row or pressing Enter on it opens that row's Sheet through a View Transition ([ADR 0006](0006-one-gated-build-component-session-per-component.md)). Opening a sheet isn't an action, since actions are async operations with a success and a failure, and the open sheet is DataTable's own state, not a screen state. Sheet joins in P1.
- **The open sheet gets one extra render.** For each DataTable with a `detail` slot, the gate harness adds one render per theme of the default screen state with the first row's Sheet open, through a library test attribute. It is gated, baselined and captured like a screen state.
- **Gate 1 rules:** at most one visible ActionBar and one visible Toast per screen state; Sheet only in a DataTable's `detail` slot; a Toast only in a state some action's `to` enters, never the default state; an ActionBar's Button carries an `action`; a Toast inside an ActionBar has tone failure, and a failure Toast in a state that shows an ActionBar sits inside it.
- **Registry `use` lines name the structure,** because the spec step can't build a transition it can't find. ActionBar: "the bulk-action bar; put the action's Button here, show it `when: [rows-selected]`, and leave it out of the success state so it becomes that state's Toast. Keep it in the failure state too, so the admin can retry with the rows still selected", since "the bar stays" on failure only if its `when` names the failure state. Toast: "the live result of an action; only in a state an action enters". Sheet: "row detail; only in a DataTable's `detail` slot". DataTable's line names its `detail` slot.
- **`action-transitions`, a P1 render-time taste rule,** checks that the motion is triggered. For each declared action the harness clicks its Button, found by its literal label, under the success and the failure fixture variant, and checks that the Screen enters `to.success` or `to.failure` through a View Transition of type `confirm` or `fail`. Whether the motion looks right is gated in the library's own stories.
- **The pass criterion is `requires.transitions`** ([ADR 0008](0008-eval-runs-are-a-budgeted-script-compared-after-the-fact.md)), each name a structural pattern checked on the final UI spec. `row-to-sheet`: a DataTable whose `detail` slot holds a Sheet. `bar-to-toast`: an action whose Button sits in an ActionBar shown `when` the action can be triggered, and whose `to.success` state shows a Toast and not that ActionBar. The stagger isn't its own key.
- **A new P1 brief carries the pay confirmation** (e.g. `bulk-pay`). The P0 five stay as written, so eval versions still compare.
- **Figma gets no motion** beyond the `TIMING` and `EASING` variables ([ADR 0007](0007-figma-sync-is-a-generated-one-call-script.md)). Captures stay still renders of each screen state and of the sheet-open render.

## Considered options

- **Named transitions on actions or states** (`transition: "bar-to-toast"`): explicit, and easy for the model to find, but they repeat what the structure already implies, and gate 1 would need a rule to keep the two consistent. This is the fallback: if eval runs show `requires.transitions` failing because the model misses the structure, add a named-transition hint on actions and hold it consistent in gate 1.
- **Motion props on nodes** (`enter="slide"`, `stagger`): a taste knob in the model's hands.
- **The code step calling `startViewTransition` itself:** every rep would wire motion its own way.
- **One component whose success form is the toast:** simpler pairing, but a standalone Toast would be a second component.
- **A `detail-open` screen state:** moves open-row state into the UI spec and fixtures for the sake of one render.
- **No motion pass criterion:** presence-only `requires.components` can't see placement, so a Sheet anywhere would pass.

## Consequences

- A third signature transition means library work and a new pattern, not a new name.
- ActionBar and Toast are coupled through a shared view transition name, which gate 1's one-of-each rule keeps unique.
