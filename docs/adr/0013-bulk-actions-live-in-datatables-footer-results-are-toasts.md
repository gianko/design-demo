# Bulk actions live in DataTable's footer; results are toasts

[ADR 0011](0011-motion-follows-declared-state-changes-owned-by-the-library.md) gave a table's bulk action an ActionBar: a raised bar, shown `when: [rows-selected]`, that held the action's Button and became the success Toast in place. On the kept bulk-pay screen it read as a slab floating apart from the table it acted on, it popped in and out as the first row was ticked and the last unticked, and it was a second node every screen with a bulk action had to wire, with a screen state, a `when` and gate 1 rules of its own. So the bulk action moves into the table. DataTable gains an `actions` slot, drawn as a footer inside its frame below the rows and always shown, with a count of the selected rows at its start; the selection stops being a screen state; and an action's result is a toast fixed to the window's corner that slides in and out, not the bar turned into a toast. Prior art went every way: MUI Table and Carbon put bulk actions in a toolbar above the table, Polaris in a bar stuck to the bottom of the viewport, tablecn in a floating bar, and shadcn and MUI DataGrid have a footer with a selected count but no bulk actions. The footer follows the last two and puts the actions in it. This supersedes part of ADR 0011 and amends [ADR 0004](0004-flat-library-only-ui-spec-and-zod-first-registry.md). Decided in [ADR 0013: bulk actions live in DataTable's footer; results are toasts](https://github.com/gianko/design-demo/issues/295).

## Decisions that come with it

- **DataTable's `actions` slot is its footer.** The slot is allow-listed to Button, and each Button in it carries an `action`. It is drawn inside the table's frame, below the rows, set off from them by a `line` rule, with its Buttons at the end edge. It follows density as the rows do, and on a phone the count and the Buttons wrap rather than spill. The footer shows whenever the table does, with no rows too (its Buttons disabled); an empty state's EmptyState takes the table's place, footer and all.
- **A table is selectable exactly when it has `actions`.** Each row and the header get a Checkbox, as `selectable` gave them, and a table without `actions` has neither checkboxes nor a footer. The `selectable` prop goes. Only a table with a footer has a selection, so a Button anywhere else, such as a PageHeader's `actions`, can't act on one.
- **The footer's Buttons are disabled until a row is ticked.** With nothing ticked they are natively disabled ([design brief](../design-brief.md): a disabled control keeps its intent's shape and leaves the tab order); ticking the first row enables them, and they change with the row's `selected` fill, at `base` with `standard`.
- **The selection locks while a footer action is pending.** Every Checkbox is `aria-disabled`, still focusable, and ticking does nothing until the action settles, so the rows the operation acts on are the rows shown ticked. A confirmed result clears the selection inside the `confirm` transition's update, and a failed one keeps it, as in ADR 0011.
- **The selected count.** The footer's start edge says how many rows are ticked, from DataTable's `selectionText`, required when it has `actions`: `{ none, one, other }`, each literal UI spec copy, the `other` form holding `{count}`, which the library replaces with the number of ticked rows (`"No invoices selected"`, `"1 invoice selected"`, `"{count} invoices selected"`). `none` shows with nothing ticked, `one` with one row, `other` otherwise. The UI spec gives the words and the library only the number, so neither writes the other's copy; [#238](https://github.com/gianko/design-demo/issues/238) ruled a count out because one side would have had to, and ADR 0004 is amended to allow the `{count}`. The count is plain text, not a live region: the Checkbox the user just ticked already says what changed.
- **The selection is DataTable's own state, not a screen state.** `rows-selected` is gone: ticking rows enters no screen state and runs no View Transition, and no UI spec, fixture variant or screen brief names it. DataTable owns ticking and the `ScreenHost` holds the selection, as in ADR 0011, and `useSelectedRows()` still reads it. A fixture variant may still name a starting selection, such as a failure variant that keeps the rows ticked for a retry.
- **The ticked rows get one extra render.** For each DataTable with `actions`, the gate harness adds one render per theme of the default screen state with rows ticked, set from the start as the open-sheet render opens its Sheet, and gates, baselines and captures it like a screen state. It shows what the `rows-selected` renders showed.
- **The body scrolls under a 10-row cap.** The table's scrolling body is at most the header row plus 10 rows at the density's row height, a size token per density; the footer sits below it, outside the cap, so the whole frame is that plus the footer. A longer table scrolls inside its body, its header row sticky with an opaque fill; the footer sits outside the scrolling body, so the count and the Buttons stay in view. Sideways scrolling on a narrow screen works as before, and the cap is the same on a phone. A focused row or Checkbox scrolled out of view scrolls back clear of the header, not under it.
- **An action's result is a Toast in the window's corner.** It is fixed to the window's bottom end corner, inset by the density's page padding and above page content at `z-toast`; on a phone it spans the width within the page padding, at the bottom. It isn't in the page flow, so where it sits in the tree moves nothing: a UI spec puts it last in its Screen, in the state its action enters, tone success in `to.success` and tone failure in `to.failure`. It shares no view transition name with anything.
- **It slides in and out from the end edge.** A success Toast slides in during the `confirm` transition that flips the statuses, at `slow` with `ease-settle`; a failure Toast at `slow` with `standard`. Either slides back out to the end edge at `slow-exit` with `exit`. No fade and no scale. Under reduced motion it is a `fast` crossfade.
- **A success Toast dismisses itself; a failure Toast stays.** A success Toast leaves after a `toast` timeout token (about 5s, `motion.timeout.toast`), its timer paused while the Toast is hovered, while focus is within it or while the tab is hidden, and resumed after. A failure Toast has no timer: it stays until its close button or the next result. Both have a close button, the internal IconButton labelled by a UI spec `closeLabel`, as Sheet's is. One Toast shows at a time, so a new result replaces the current one, and a Toast shows again each time its state is entered, even after it was closed or timed out.
- **Whether the Toast shows is the library's own state,** like the open Sheet. The screen stays in its state (such as `payment-scheduled`) after the Toast leaves, so dismissing it changes no screen state and the UI spec names none. Gate renders and Figma captures show the Toast with its timer paused, so they are deterministic.
- **Announcements don't change.** A Toast's copy is announced politely through Screen's one status region each time its state is entered, a failure's included.
- **Gate 1 rules.** The ActionBar rules go: one visible ActionBar per state, its Button carrying an `action`, a Toast inside it being a failure, and a failure Toast sitting inside it. These stay: at most one visible Toast per screen state, and a Toast only in a state some action's `to` enters, never the default state. These are new: a DataTable's `actions` allows only Button, and each carries an `action`; a DataTable with `actions` gives `selectionText`; and its `other` form holds `{count}`.
- **Registry `use` lines.** ActionBar's entry goes. DataTable's names the footer: put the action's Button in `actions` and give `selectionText`, and only a table with `actions` is selectable. Toast's no longer places it where the bar was: last in the Screen, in the state its action enters.
- **The pass criterion `bar-to-toast` becomes `table-action-to-toast`:** a DataTable whose `actions` slot holds a Button running an action whose `to.success` state shows a success Toast and whose `to.failure` state shows a failure Toast. `row-to-sheet` is unchanged ([ADR 0008](0008-eval-runs-are-a-budgeted-script-compared-after-the-fact.md)).

## Considered options

- **A toolbar above the table** (MUI Table, Carbon): the action sits at the top while the eye ends at the rows just ticked, a long table would need the toolbar to stick, and Carbon's swaps in for the table's own toolbar when rows are ticked, the same pop the bar had.
- **Buttons that appear only once a row is ticked:** the bar's pop-in again, and the footer's height would change with the selection. Disabled Buttons show the action is there before anything is ticked.
- **A page that scrolls, with a sticky footer** (close to Polaris's bar): the footer would stick to the window's bottom while its table scrolled away under it, coming apart from the frame it belongs to, the slab again.
- **A table that fills the window:** its height would depend on the viewport and everything above it, so a render would show a different number of rows on every screen size. The cap shows the same 10.
- **The result inline, in the footer or above the table:** in the footer it competes with the count and the Buttons in a strip sized for controls; above the table it is out of view once the table has scrolled. Neither is the toast the design brief's signature transition ends on.
- **Assertive announcements for a failure:** the user is waiting on the result of their own action, so a polite announcement reaches them, and one region at one politeness keeps announcements in order.
- **Library-owned count copy, or a count in the Button's label** (`"3 selected"`, `"Approve and pay 3"`, the alternatives in #238): the first puts words in the library; the second changes the Button's width with every tick and reads wrong as `"Approve and pay 0"`.

## Consequences

- A screen with a bulk action has one node and one screen state fewer to wire, and the spec step has no `when` to get right for it. Signature transition #1 loses the morph from bar to toast and gains the slide.
- `rows-selected` leaves the fixtures, the screen briefs, the kept bulk-pay screen and the generator's UI spec fixtures, and its renders' baselines give way to the ticked-rows render's.
- Eval runs before and after this aren't comparable on bulk-pay, overdue-invoices and failed-payments, whose components, states and transitions change; accepted. invoice-queue changes too, against ADR 0011's "the P0 five stay as written": its Approve and pay Button moves from the PageHeader into the table's footer and its `rows-selected` goes, so its runs don't compare either.
- A success Toast leaves without the user acting, which bends the brief's "motion only when the user acts". It is accepted because the result stays on the screen in the flipped statuses and was announced, a failure, which the user has to read and act on, never leaves on its own, and the timer pauses on hover and focus. `.out-of-scope/toast-dismissal.md` ([#242](https://github.com/gianko/design-demo/issues/242)) is retired with it, as are the notes on the bar's count (#238) and on its entrance not rising ([#237](https://github.com/gianko/design-demo/issues/237)), whose "when to reconsider" a toast that slides in on its own meets.
- A confirmed result clears the selection and so disables the footer's Button that had focus; a disabled Button can't hold focus, and ADR 0011's focus rule moves focus only when the focused element leaves the document. So when a footer Button that holds focus becomes disabled, focus moves to the table, next to what was acted on, and the table shows the focus ring, so a keyboard user sees where focus went. Not into the Toast, where focus within would hold a success Toast's timer, and not to the Screen, which is further from the rows. The result still reaches assistive tech through the polite announcement.
